  -- (d) Why Price_per_SqFt must NOT be used as an ML feature

  DATA LEAKAGE explained simply:

  When you train a model, you show it 'inputs' and ask it to
  predict an 'output'.  Here:
    INPUT  (features) = City, BHK, Size, Year_Built, ...
    OUTPUT (target)   = Price_in_Lakhs

  Price_per_SqFt is computed FROM Price_in_Lakhs:
    Price_per_SqFt = (Price_in_Lakhs x 100,000) / Size_in_SqFt

  So if the model sees Price_per_SqFt as an input, it has ALREADY
  seen a transformed version of the answer it's supposed to predict.
  This is like letting a student see the answer key during an exam.

  In practice the model would score perfectly on training data but
  fail completely on real new listings — because new listings won't
  have a price yet (that's the whole point of prediction!).

  CONCLUSION: Drop Price_per_SqFt before any modelling step.

  INVESTIGATION 3 — Age_of_Property vs. Year_Built
========================================================================

  -- (a) Is Year_Built + Age_of_Property constant?

  Rows checked       : 250,000
  Min of (Y + A)     : 2025
  Max of (Y + A)     : 2025
  Spread (max - min) : 0 years
  Unique values      : 1

  FINDING: Year_Built + Age_of_Property = 2025 for EVERY row.
  This is a perfect mathematical identity — no exceptions.

  -- (b) What this tells us about how Age was created

  If Year_Built + Age = 2025 for every row, then:

    Age_of_Property = 2025 - Year_Built

  This means Age was NOT collected separately — it was COMPUTED
  from Year_Built using 2025 as the reference year.

  IMPLICATION 1 — Redundancy:
    Age and Year_Built carry identical information.  Using BOTH
    as model features is redundant (like using Celsius and Fahrenheit
    temperature simultaneously).  Keep only one.

  IMPLICATION 2 — No information loss:
    Either column fully represents the property's age.  The choice
    between them is a modelling preference, not a data problem.

  -- (c) Risk of using the 'current year' instead of 2025

  Suppose a future user runs the model in 2027 and tries to re-derive
  age from Year_Built using 'today's year':

    New age = 2027 - Year_Built

  For a property built in 2010:
    Dataset age    =  2025 - 2010 = 15 years
    Re-derived age =  2027 - 2010 = 17 years  (2 years off)

  This 2-year gap can shift predicted prices if the model learned
  that age of 15 = one price tier and age of 17 = a lower tier.

  RECOMMENDATION:
    - Use Year_Built as the feature (absolute, never changes).
    - Document that Age_of_Property = 2025 - Year_Built.
    - Do NOT compute Age dynamically at prediction time unless
      the model was retrained with that convention.
    - Do NOT assume 2025 is the real data-collection year;
      it is only the value embedded in the formula.
